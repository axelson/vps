## What Diverged from the Plan

### Step 1: nerves_system_vultr removed entirely

The plan said to resolve the `nerves_system_br` version conflict by bumping to `1.33.2`. In practice, `nerves_system_vultr 0.27.1` hard-requires `nerves_system_br 1.30.1`, creating an irresolvable conflict. Since the `:vultr` target is being retired anyway, the fix was to:

- Remove `:vultr` from `@all_targets` in `mix.exs`
- Remove the `nerves_system_vultr` dep entirely
- Remove `nerves_system_br` explicit pin (no longer needed)

### Step 2: OTP version mismatch

`nerves_system_x86_64 ~> 1.33` targets OTP 28 (ERTS 16.2). The host was running OTP 27. Mix firmware fails silently or with confusing errors when the host OTP doesn't match the target OTP.

Fix: install matching versions via asdf:
```sh
asdf install erlang 28.4
asdf install elixir 1.19.5-otp-28
```
Updated `.tool-versions` accordingly.

### Step 7: Bootstrap approach changed completely

The plan described using Alpine Linux installed as the Vultr OS. The actual path taken was more roundabout:

**Attempt 1: cloud-init**
Tried using Vultr's cloud-init userdata to run `fwup` on first boot. Problem: `fwup -a -i vps.fw -d /dev/vda -t complete` fails with `fwup: Error calling umount on '/'` — you can't write firmware to the disk you're booted from. Tried `fwup --unsafe` (skips unmount check) — still failed. Tried `umount -l /` (lazy unmount) — disconnected SSH and rebooted the machine.

**Attempt 2: iPXE**
Vultr supports iPXE custom scripts. Tried downloading Alpine ISO and the firmware via iPXE `chain`/`initrd` commands. Hit repeated TLS errors:
- `dl-cdn.alpinelinux.org`: error `410de13c` — iPXE's TLS implementation doesn't trust Alpine's CA
- `github.com` releases: error `2d0c613b` — GitHub uses TLS features (likely ECDSA or TLS 1.3) that Vultr's iPXE build doesn't support
- `raw.githubusercontent.com`: same error

iPXE on Vultr has a broken/outdated TLS stack that can't reach most modern HTTPS hosts. Abandoned.

**Attempt 3: custom initrd (failed)**
Tried building a custom initrd with busybox + fwup that iPXE could load. The Docker build command using a heredoc inside `sh -c '...'` failed silently (heredoc doesn't work that way in sh). Also used brace expansion (`{bin,proc,...}`) which plain `sh` doesn't support. The resulting initrd was 397 bytes (broken).

Fixed the build:
- Wrote the init script to `/tmp/nerves-init` as a real file, mounted into Docker
- Listed directories individually instead of using brace expansion
- Got a valid 8MB initrd

But at this point, the simpler Vultr ISO approach was available:

**Attempt 4: Vultr Custom ISO (what actually worked)**
Vultr lets you boot from a custom ISO URL. Uploaded Alpine Linux standard ISO URL (`https://dl-cdn.alpinelinux.org/alpine/latest-stable/releases/x86_64/alpine-standard-3.23.3-x86_64.iso`). VM boots into Alpine live environment from a virtual CD-ROM — `/dev/vda` is free to write.

Notes from the Alpine live session:
- Network not configured by default: need `ip link set eth0 up && udhcpc -i eth0`
- `fwup_1.15.0_x86_64.tar.gz` on GitHub releases is a 404 — the correct file is `fwup_1.15.0_amd64.deb`; install with `dpkg -i`
- Alpine ISO URL `3.21.3` gives 404 — latest at the time is `3.23.3`
- `apk add fwup` fails — fwup is in the community repo, not enabled by default

Full working install command (single compound):
```sh
ip link set eth0 up && udhcpc -i eth0 \
  && echo "https://dl-cdn.alpinelinux.org/alpine/latest-stable/community" >> /etc/apk/repositories \
  && echo "https://dl-cdn.alpinelinux.org/alpine/latest-stable/main" >> /etc/apk/repositories \
  && apk update && apk add fwup e2fsprogs \
  && wget -O /root/vps.fw https://github.com/axelson/vps/releases/download/x86-poc-v1/vps.fw \
  && fwup -a -i /root/vps.fw -d /dev/vda -t complete \
  && echo b > /proc/sysrq-trigger
```

### First boot: EXT4 error

On first boot, Nerves crashed with an EXT4 error mounting `/dev/vda4`. The `fwup complete` task wipes the app partition with `raw_memset` (fills with `0xff`) rather than formatting it as ext4. `nerves_runtime`'s `Init` GenServer is supposed to detect this and format it — but it runs after erlinit tries to mount, and erlinit's mount fails first.

Fix: booted Alpine ISO again and ran `mkfs.ext4 /dev/vda4` manually, then rebooted. On subsequent boots `nerves_runtime` will handle any re-formatting needs.

### Second boot: Erlang crashing (Erlang output not visible)

After the ext4 fix, Nerves started further but the Erlang VM was crashing. The crash dump showed `{application_terminated,kernel,shutdown}` with Exqlite NIF in taints. The IEx console was configured to go to `ttyS0` (serial port) — but Vultr only exposes VGA via noVNC. So there was no way to see the actual error.

Root cause of invisibility: `config/nerves, erlinit: [...]` in `target.exs` didn't set `ctty`, so it inherited `--ctty ttyS0` from the system's `erlinit.config`.

Fix: added `ctty: "tty1"` to the project erlinit config in `config/target.exs`. Also:
- Increased `HEART_BEAT_TIMEOUT` from 30 to 120 seconds in `rel/vm.args.eex`
- Removed `config :site_encrypt, sites: [{VpsWeb.Endpoint, VpsWeb.SiteEncryptImpl}]` from `target.exs` — `VpsWeb.SiteEncryptImpl` doesn't exist (leftover from an older site_encrypt API), replaced with a comment

After rebuilding and reflashing (via Alpine ISO again), the IEx prompt appeared on the noVNC console and the app started cleanly.

## Key Findings

### `/data` is a symlink to `/root`

The `nerves_system_x86_64` rootfs has `/data -> /root` as a symlink. The app data partition is mounted at `/root` by erlinit. So `/data/vps.db`, `/data/site_encrypt`, and `/data/.target.secret.exs` all work correctly — they resolve through the symlink to the writable ext4 partition.

### ctty must be tty1 for Vultr (VGA-only)

Vultr VMs have no serial console. The default `--ctty ttyS0` in the x86_64 erlinit.config sends all Erlang output to serial and makes debugging via noVNC impossible. Always set `ctty: "tty1"` in `config/target.exs` for this deployment.

### Restarting the system from IEx

Use `Nerves.Runtime.reboot()` to restart the whole system (not just the Erlang VM). `:init.restart()` only restarts the BEAM — it re-runs config providers and restarts OTP apps, which is useful after writing `/data/.target.secret.exs`. But if you need a full reboot (e.g. after flashing new firmware), use `Nerves.Runtime.reboot()`.

### nerves_heart HEART_BEAT_TIMEOUT

The default in `rel/vm.args.eex` was 30 seconds. On a fresh boot with Let's Encrypt ACME initialization, database creation, etc., this may be tight. Bumped to 120 seconds.

### site_encrypt self-signed cert on first boot

On first boot with `cert_mode: "production"`, site_encrypt generates a self-signed cert and serves that while waiting for Let's Encrypt. HTTPS works immediately (with cert warning). Real certs are issued either:
- On the next scheduled run (3:32 AM UTC — `periodic_offset` from config)
- Immediately via `SiteEncrypt.force_certify(VpsWeb.Endpoint)` from IEx

### fwup releases naming convention

The GitHub release asset for fwup uses `amd64` (Debian naming) not `x86_64` (Linux naming) for the `.deb` file. The tarball (`x86_64.tar.gz`) is a 404 at `v1.15.0`. Use `fwup_1.15.0_amd64.deb` with `dpkg -i`.

## SSL Certificate Gotcha During Cutover

`SiteEncrypt.force_certify/1` returned `:error` after ~2 minutes on the new server. The cause: `site_encrypt_domains` lists **all 5 domains** in a single cert, but `depviz.jasonaxelson.com` DNS still pointed at the old server. Let's Encrypt validates HTTP-01 challenges for every domain in the cert — it hit the old server for depviz, got no challenge token, and failed after 60 retries × 2 seconds.

Fix: temporarily removed `depviz` from `site_encrypt_domains` in `/data/.target.secret.exs`, issued the cert for the other 4 domains, then migrated depviz DNS and added it back with a brief downtime. (Zero-downtime alternative: configure the old server to redirect `/.well-known/acme-challenge/*` to the new server IP — Let's Encrypt follows redirects for HTTP-01 challenges.)
